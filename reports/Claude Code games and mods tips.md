# Build phone games in small, cheap steps

**You can make and play real browser games using only an Android phone.** The method that works best is simple. Put the game in a free GitHub project (a "repo", which is just an online folder for code). Start a Claude Code cloud session on it from the **Code** tab of the Claude app. Ask for a single `index.html` page. Then have Claude save and upload ("commit and push") after every working change, so a free GitHub Pages link shows the new version on your phone **about 30 seconds later** ([Simon Willison](https://simonwillison.net/2026/Aug/5/raccoon-heist/)). Good games come from many small rounds, not one big request: a one-message build gives you a working start but a shallow game ([Simon Willison](https://simonwillison.net/2026/Aug/5/raccoon-heist/)). On the "mods" side, the key fact is that **cloud sessions only see what is saved inside your repo or switched on in your claude.ai account**. That means a short `CLAUDE.md` rules file, skills and hooks saved in the repo's `.claude/` folder, and skills or connectors you enable on claude.ai. Most famous mods (status bars, sounds, desktop alerts, the `/plugin` command) need a computer and do nothing on a phone ([Cloud environments docs](https://code.claude.com/docs/en/cloud-environments)). With low weekly credits, the habits that matter most are: one task per session, `/clear` between unrelated jobs, the cheaper Sonnet model for routine edits, and asking for testing only at milestones.

## Your phone is a remote control; the game is built in the cloud

The Claude app **does not run code on your phone**. It is "a client for Claude Code sessions rather than a place where code runs" ([Claude Code mobile docs](https://code.claude.com/docs/en/mobile)). When you tap **Code**, pick a repo and a branch (a separate line of work inside the repo), and type your request, the work happens on an Anthropic computer in the cloud. It **keeps running after you lock your phone**. Cloud sessions come with Pro, Max, Ultra and Team plans and **use your normal plan allowance, with no extra charge** for the cloud computer ([Cloud sessions docs](https://code.claude.com/docs/en/claude-code-on-the-web)). The repo must be on GitHub. To create one, go to github.com/new in your phone browser. You may need to close and reopen the Claude app before the new repo shows up ([Simon Willison TIL](https://til.simonwillison.net/claude-code/preview-github-pages)).

That cloud computer is well equipped. It includes Node (a tool for running JavaScript), Python, Java, git and **a real Chrome browser that Claude can drive by itself**. The Android tools needed to build apps are *not* included ([Cloud environments docs](https://code.claude.com/docs/en/cloud-environments)). Its internet access is "Limited" by default: package stores like npm and GitHub are allowed, but other websites are blocked until you add them to the environment's **Allowed domains** list ([Cloud environments docs](https://code.claude.com/docs/en/cloud-environments)). After a few idle minutes the session pauses and keeps your files, and your next message wakes it. If it stays idle for a long time, the conversation comes back but any program still running in the background does not ([Cloud environments docs](https://code.claude.com/docs/en/cloud-environments)). The fix is easy: **always ask Claude to commit and push**, because pushed work is safe on GitHub forever.

There are three permission modes you can switch between from the app: **Plan** (Claude only plans), **Accept edits**, and **Auto**. "Bypass permissions" cannot be chosen from the app ([Claude Code mobile docs](https://code.claude.com/docs/en/mobile)). When Claude pushes, a **Changes card** shows lines added and removed. Tap it to see the edits, and you can leave comments on specific lines that go to Claude with your next message ([Cloud sessions docs](https://code.claude.com/docs/en/claude-code-on-the-web)).

## A five-step loop turns every push into a playable link

The best-documented phone-only method comes from Simon Willison, who built a full 3D game from his phone in August 2026 ([Simon Willison](https://simonwillison.net/2026/Aug/5/raccoon-heist/)). Here it is in plain steps:

| Step | What you do | Where |
|---|---|---|
| 1 | Create an empty repo (tick "add a README") | github.com/new in your phone browser |
| 2 | Start a cloud session on it and send your first prompt (below) | Claude app, Code tab |
| 3 | When Claude makes its `claude/...` branch, open repo **Settings → Pages**, keep "Deploy from a branch", choose that branch | Phone browser (tap "Desktop site" if the page is cramped) |
| 4 | Open `https://YOURNAME.github.io/REPONAME/` and play | Phone browser |
| 5 | Ask for one change, wait for the push, reload, repeat | Claude app |

Two GitHub limits matter here. **Free GitHub accounts get Pages only for public repos**. Private-repo Pages needs GitHub Pro ([GitHub plans](https://docs.github.com/en/get-started/learning-about-github/githubs-plans)). And even a private repo's Pages link is only "secret", meaning **anyone who guesses the address can play it** ([Simon Willison TIL](https://til.simonwillison.net/claude-code/preview-github-pages)). After you merge the work into the main branch, switch Pages back to main.

Willison's first message set all the rules up front: browser only, static files, `index.html` as the start page, **phone support required (touch controls, small screens)**, "Commit and push as often as possible so I can preview your work", "Work independently - do not ask me to make any further design decisions", and a `notes.md` build log updated with every commit ([Simon Willison](https://simonwillison.net/2026/Aug/5/raccoon-heist/)). Here is a starter prompt built from those rules plus tips from other game makers. You can paste it or say it aloud:

```
Make a [type of game] as a simple website with index.html at the top of the repo.
It must work on an Android phone held upright: touch controls, fits any screen.
No build step. Copy any libraries into the repo instead of loading them from the web.
Put all tunable numbers (speed, gravity, enemy count) in one CONFIG object at the top.
Keep notes.md updated with what you did and what's next.
Commit and push every time something works. Work on your own; don't ask me design questions.
Before saying you're done, screenshot it at phone size and check it yourself.
```

After that, **build one feature per message**. A Breakout clone grew through "quick little iterations", for example adding a multi-ball power-up as its own step ([Les Orchard](https://blog.lmorchard.com/2025/07/10/breakout-with-claude/index.md)). The "develop-web-game" skill gives the same advice: **change one thing at a time, fix the first new error before going on**, and keep a `progress.md` with your original idea at the top and a to-do list below ([vibehackers.io](https://vibehackers.io/claude-code/skills/develop-web-game-davila7)). For bigger ideas, switch to **Plan** mode first. Anthropic recommends planning complex tasks and giving clear targets rather than vague requests like "improve this" ([Claude Code costs docs](https://code.claude.com/docs/en/costs)). Ask Claude to write a short game design file, read it, approve it, then build one milestone at a time.

Describe the *feel* you want in concrete words. A roguelike developer found that **detailed descriptions of what a feature does, how it looks and how you interact with it** got the best results. He spoke his descriptions with voice typing, and he expected to spend the most rounds on menus and graphics, where the AI struggles most ([Liminal Warmth](https://liminalwarmth.substack.com/p/claude-code-context-lessons)). He also warns that AI tends to over-engineer. If a branch gets messy, throw it away and restart, because that is cheap ([Liminal Warmth](https://liminalwarmth.substack.com/p/claude-code-context-lessons)). Claude also tends to scatter hard-coded numbers through the code, which is why the starter prompt asks for one CONFIG object ([Playgama](https://playgama.com/blog/business-faqs/how-to-use-claude-code-for-developing-browser-games-via-cli/)). A good habit is to get the basic game loop fun first, and only then ask for "juice": screen shake, particles, little bounces and sounds.

**Use git as save points.** Every commit is a save point you can go back to. Mixing many features into one commit makes it impossible to find what broke things ([buildtolaunch](https://buildtolaunch.substack.com/i/194132798/skipping-version-control)). You never have to type git commands. Just say "undo the last change and push" or "go back to the version from before the shop was added", and Claude does it.

## Make Claude play-test at phone size before you do

Your phone browser has no developer tools for seeing errors, so **let Claude test inside its own cloud browser**. Willison had Claude use Playwright (a tool that lets a program click and tap through a web page) with the built-in Chrome to take screenshots at desktop, phone-upright and phone-sideways sizes, and to script full playthroughs: pickups, enemy chases, winning, losing and restarting ([Simon Willison](https://simonwillison.net/2026/Aug/5/raccoon-heist/)). Even so, **desktop-size tests missed bugs that only showed on a real phone**. The game drew at double size, and an invisible overlay blocked taps. So tell Claude to test with real phone screen settings ([Simon Willison](https://simonwillison.net/2026/Aug/5/raccoon-heist/)). A ready-made phrase: *"Screenshot at 390x844 with deviceScaleFactor 3 and look at it before telling me it's done."*

Two tricks make Claude's tests much better. First, have the game report its own state as text (`window.render_game_to_text`, giving player position, enemies, score and so on), so Claude can "see" the game without guessing from pictures. Second, add a step-forward-in-time control (`window.advanceTime(ms)`) so every test run behaves the same way ([vibehackers.io](https://vibehackers.io/claude-code/skills/develop-web-game-davila7)). Screenshot tests of moving games are unreliable unless the random numbers, the clock and the screen size are fixed ([skillselion](https://skillselion.com/skills/chongdashu/phaserjs-oakwoods/playwright-testing)). For your own checks on the phone, David Wolgemuth added **eruda, a small on-page debug console**, because phone browsers lack one. He also had tests save game situations as tappable links, so he could jump straight to a tricky moment ([David Wolgemuth](https://david-wolgemuth.github.io/2026/01/01/vibe-coding-from-phone.html)). A simpler version is to ask for a debug panel that only appears when you add `?debug=1` to the address.

Phone browsers have their own traps. Ask Claude to handle each of these by name:

| Problem on phone | What to ask for |
|---|---|
| Game looks tiny or zoomed out | A `width=device-width` viewport tag; size the canvas from the screen size × devicePixelRatio, capped at 2 ([Cinevva](https://app.cinevva.com/tutorials/mobile-friendly-web-games)) |
| Swiping reloads the page | `touch-action: none` on the game canvas ([mobile-game-controls skill](https://raw.githubusercontent.com/trojan-lord/hermes-cuso/main/skills/mobile-game-controls/SKILL.md)) |
| Hard to move | A joystick that appears wherever your thumb lands, plus a big action button ([Simon Willison](https://simonwillison.net/2026/Aug/5/raccoon-heist/)) |
| Title art cut off | Check art on several screen shapes ([Simon Willison](https://simonwillison.net/2026/Aug/5/raccoon-heist/)) |
| No sound, lost progress, slow phone | Start audio on the first tap, save progress in browser storage, pause when you switch apps, prefer simple 2D (Canvas or Phaser) on cheaper phones |

The last row is practical advice from the research team, not from a single cited source. **Copy libraries into the repo** rather than loading them from the web, so the game is self-contained ([Simon Willison](https://simonwillison.net/2026/Aug/5/raccoon-heist/)). This also helps Claude's own tests, because the cloud computer's limited internet may block some library websites ([Cloud environments docs](https://code.claude.com/docs/en/cloud-environments)). Willison's earlier recipe loaded libraries from the web and that worked too, but copying them in is the safer default.

Testing costs credits. **Ask for full play-tests at milestones, not after every small tweak.**

## Free art, sound, hosting and an Android app, with no computer

**Art and sound can cost nothing.** Kenney's game art packs are public domain (CC0): free for any use, with credit optional ([Kenney](https://kenney.nl/support)). For sound effects, jsfxr ([GitHub](https://www.github.com/chr15m/jsfxr)) and the tiny ZzFX ([npm](https://npmjs.com/package/zzfx)) **create retro sounds directly in code, with no sound files**. The cheapest path is to have Claude draw everything with shapes, gradients or emoji first and swap in real art later. If the cloud computer can't download an art site, upload the files to your repo through the GitHub website, or add the site to Allowed domains. For any art that is not CC0, ask Claude to keep a `CREDITS.md`. Willison also gave Claude an image-generation key for textures, with prompts ending "no text, no words, no logos". He found a picture can look right as a file but be applied wrongly in the game, so check it in play ([Simon Willison](https://simonwillison.net/2026/Aug/5/raccoon-heist/)). Store keys like that as a **network secret** in the environment settings, never in the chat or in the code ([Cloud environments docs](https://code.claude.com/docs/en/cloud-environments)).

**Sharing:** GitHub Pages is the easiest free host. itch.io also accepts **a single HTML file, or a ZIP with `index.html` inside**, and has a "Mobile Friendly" switch that launches the game full-screen on phones ([itch.io docs](https://itch.io/docs/creators/html5)).

**Getting an "app" on your home screen:** the easy option is to ask Claude to make the game a PWA (an installable web app: a small manifest file plus offline support), then use Chrome's **Add to Home screen**. No app file is needed. For a real Android app file (APK), the phone-only route is to ask Claude to add Capacitor (a tool that wraps a web game as an Android app) plus a GitHub Actions workflow. That way GitHub's computers build the APK, because the Claude cloud computer lacks the Android tools ([Cloud environments docs](https://code.claude.com/docs/en/cloud-environments)). A **debug build** (`assembleDebug`) skips the signing-key setup ([Ionic forum](https://forum.ionicframework.com/t/how-to-build-an-android-apk-file-without-using-android-studio-in-a-capacitor-project/177814)). To install it: in your phone browser, open the repo's **Actions** tab, tap the finished run, download the file under **Artifacts** (you must be logged in), unzip it with a file app, and install it ([Home Assistant dev docs](https://developers.home-assistant.io/docs/android/tips/testing_pr_builds)). Android will ask you to allow "install unknown apps" for that app. GitHub Free includes **$12 a month of Actions build time** ([GitHub plans](https://docs.github.com/en/get-started/learning-about-github/githubs-plans)).

**Ready-made game mods are mixed.** OpusGameLabs/game-creator is the most complete game toolkit, with commands like `/make-game`, `/add-audio` and `/qa-game`. But it runs a coding helper *and* a testing helper after every step, retrying up to three times ([GitHub](https://github.com/OpusGameLabs/game-creator)). That is great for quality but **heavy on credits**, and no independent reviews of it were found. With a small allowance, a single lighter skill such as develop-web-game, plus the starter prompt above, gives most of the benefit.

## Only mods saved in your repo or your claude.ai account reach the phone

"Mods" for Claude Code come in a few kinds. **CLAUDE.md** is a rules file Claude reads at the start of every session. **Skills** are instruction packs Claude loads only when needed. **Hooks** are automatic actions, like "run the tests whenever Claude finishes". **Plugins** are bundles of the above. **Connectors** link Claude to apps like Gmail or Drive. The important rule for phone users: **a cloud session is a fresh copy of your repo**, so it only gets what is saved in the repo, what is set on the cloud environment, and what is switched on in your claude.ai account ([Cloud environments docs](https://code.claude.com/docs/en/cloud-environments)).

| Mod | Works from Android cloud sessions? |
|---|---|
| `CLAUDE.md` in the repo | **Yes.** Keep it under about 200 lines ([Best practices](https://code.claude.com/docs/en/best-practices)) |
| Skills, helpers ("agents") and commands in the repo's `.claude/` folder | **Yes**, if committed ([Cloud environments docs](https://code.claude.com/docs/en/cloud-environments)) |
| Hooks in the repo's `.claude/settings.json` | **Yes** in single-repo sessions; **no** in multi-repo sessions or project threads ([Cloud environments docs](https://code.claude.com/docs/en/cloud-environments)) |
| Skills you enable at claude.ai/customize/skills | **Yes**, loaded automatically ([Skills docs](https://code.claude.com/docs/en/skills)) |
| Connectors set up at claude.ai/customize/connectors | **Yes** ([Scheduled tasks docs](https://code.claude.com/docs/en/routines)) |
| Plugin "Add" card that Claude shows in a session | **Yes**: tapping Add turns it on for your claude.ai account ([Cloud sessions docs](https://code.claude.com/docs/en/claude-code-on-the-web)) |
| `/plugin` command, plugins listed in repo settings, anything in `~/.claude/` | **No** ([Cloud environments docs](https://code.claude.com/docs/en/cloud-environments); [Mobile docs](https://code.claude.com/docs/en/mobile)) |
| Status lines, sound alerts, desktop pop-ups, themes, keyboard shortcuts | **No.** These are computer-only |

Since you can't type `/plugin`, the phone-friendly way to install a skill is to **ask Claude to copy it into the repo's `.claude/skills` folder and push**. To get a plugin's benefit, tap its Add card, or copy its skills into the repo. One gap remains: the docs don't plainly say whether every plugin turned on in claude.ai loads in cloud sessions, so test it once before relying on it.

**The CLAUDE.md habit with the biggest payoff:** after you correct Claude, say *"Update CLAUDE.md so you don't make that mistake again, and push."* Boris Cherny, who created Claude Code, uses this habit ([Boris Cherny tips](https://snowan.gitbook.io/study-notes/ai/claude-code/boris-cherny-cc-tips)). The "push" part matters because the cloud computer is thrown away afterwards. Anthropic's advice is to put in CLAUDE.md only what Claude can't work out alone, such as the test command and things you've corrected twice. Writing in ALL CAPS is outdated advice. If a rule must never be broken, **make it a hook**, because CLAUDE.md is followed "most of the time, not every time" ([Best practices](https://code.claude.com/docs/en/best-practices)). Cherny also says anything you do more than once a day should become a saved skill or command ([Boris Cherny tips](https://snowan.gitbook.io/study-notes/ai/claude-code/boris-cherny-cc-tips)).

**Hooks worth asking Claude to add** (say: "add a hook in .claude/settings.json that…" and Claude writes it). A **"Stop" hook** that runs your tests whenever Claude finishes and sends it back to fix failures; it gives up after 8 blocks in a row so it can't loop forever ([Best practices](https://code.claude.com/docs/en/best-practices)). A **safety guard** that blocks risky commands, which works even when other permissions are loose ([Hooks guide](https://code.claude.com/docs/en/hooks-guide)), though simple pattern guards can miss variations ([dev.to](https://dev.to/boucle2026/bash-guard-stop-claude-code-from-running-dangerous-commands-95g)). A **credit-saving trimmer** that cuts long test output down to the last 100 lines, so Claude reads hundreds of words instead of tens of thousands ([Costs docs](https://code.claude.com/docs/en/costs)). A **SessionStart hook** that installs your game's tools automatically at the start; keep it quick, since it runs on every start and resume ([Cloud environments docs](https://code.claude.com/docs/en/cloud-environments)). Notification and sound hooks are popular in lists like awesome-claude-code ([awesome-claude-code](https://raw.githubusercontent.com/hesreallyhim/awesome-claude-code/HEAD/README.md)), but they are useless on a phone-only setup.

Beyond mods, a few **built-in cloud features suit phones well**. *"Watch this PR and fix any CI failures or review comments"* makes Claude babysit a pull request (a request to merge your work) for you ([Cloud sessions docs](https://code.claude.com/docs/en/claude-code-on-the-web)). **Scheduled tasks** (at claude.ai/code/routines, or `/schedule`) run a saved prompt automatically, but each run uses your allowance ([Scheduled tasks docs](https://code.claude.com/docs/en/routines)). `/rename` gives sessions real names, which helps because the session list gets cluttered ([Cloud sessions docs](https://code.claude.com/docs/en/claude-code-on-the-web)). Archive finished sessions to tidy the list.

## Six habits stretch a small weekly allowance

Cloud sessions **share one allowance with all your other Claude use**, and running several at once burns it proportionally faster ([Cloud sessions docs](https://code.claude.com/docs/en/claude-code-on-the-web)). Limits run on a rolling 5-hour window plus a weekly cap ([Costs docs](https://code.claude.com/docs/en/costs)). Anthropic doesn't publish exact token numbers per plan. The core reason long sessions get expensive is that **Claude re-reads the whole conversation on every message** ([Costs docs](https://code.claude.com/docs/en/costs)).

| Habit | Why it saves credits |
|---|---|
| **One task per session; type `/clear` between unrelated jobs** | `/clear` is free and stops old chat being re-sent every message ([Costs docs](https://code.claude.com/docs/en/costs)) |
| **`/model sonnet` for routine edits; save Opus for hard problems** | Sonnet handles most coding ([Costs docs](https://code.claude.com/docs/en/costs)). On the phone, type the name after the command; there is no picker ([Cloud sessions docs](https://code.claude.com/docs/en/claude-code-on-the-web)) |
| **Lower `/effort` for simple tasks** | Claude's "thinking" is billed, and can run to tens of thousands of tokens ([Costs docs](https://code.claude.com/docs/en/costs)) |
| **Plan first, be specific, stop early** | Plan mode, precise requests and stopping a wrong direction early avoid paying twice ([Costs docs](https://code.claude.com/docs/en/costs)). In the app, tap ✕ to take back a queued message ([Cloud sessions docs](https://code.claude.com/docs/en/claude-code-on-the-web)) |
| **After two failed fixes, start fresh with a better prompt** | Endless correction loops waste the most ([Best practices](https://code.claude.com/docs/en/best-practices)) |
| **Avoid background spenders** | `/loop`, scheduled tasks, helper agents and agent teams all spend while you're away; agent teams can use about **7x** the tokens ([Costs docs](https://code.claude.com/docs/en/costs)) |

Two smaller points help too. Coming back to a long session after a break reprocesses everything, so **if you don't need the old chat, a new session is cheaper** ([Best practices](https://code.claude.com/docs/en/best-practices)). Before each new session, have Claude keep `notes.md` current, so a fresh session can pick up with one line: *"Read notes.md and do the next to-do."* Wolgemuth used the same "zero-thought" opener with a backlog file ([David Wolgemuth](https://david-wolgemuth.github.io/2026/01/01/vibe-coding-from-phone.html)). Also keep CLAUDE.md short and move long instructions into skills, since CLAUDE.md is loaded every session but a skill only loads when used ([Costs docs](https://code.claude.com/docs/en/costs)). To check usage on Android, look at your usage page in claude.ai settings.

**Voice typing** saves thumbs, but read the text before sending. Coding agents follow words literally, so a stray "um, no wait" can become an instruction ([AssemblyAI](https://assemblyai.com/blog/voice-coding-dictate-to-coding-agents)). The Claude app's microphone works on Android ([Claude Help Center](https://support.claude.com/en/articles/10065434-using-dictation-on-claude-mobile)), but one user reported it missing from the Code screen ([GitHub issue](https://github.com/anthropics/claude-code/issues/36581)). Your keyboard's voice button always works as a backup.

## What does not work from an Android phone

| Doesn't work on phone-only | Use instead |
|---|---|
| `/plugin`, `/resume`, `/web-setup`, `--teleport` | Add cards, repo `.claude/` files, renamed sessions in the list |
| Remote Control and Dispatch (they need your own computer switched on) ([Mobile docs](https://code.claude.com/docs/en/mobile)) | Cloud sessions |
| Running or previewing the game inside the Claude app (no documented preview pane) | GitHub Pages link, or an artifact (a private Claude-hosted web page) |
| Phone push alerts when a cloud task finishes (documented only for Remote Control) | Check back later; work keeps going while the phone is locked |
| Status lines, sound/desktop alert hooks, themes, keyboard shortcuts | Nothing needed |
| Personal settings in `~/.claude/` | Repo files, claude.ai skills, or an environment setup script |
| Building Android apps on the Claude cloud computer (no Android tools installed) | GitHub Actions builds the APK |
| GitLab or Bitbucket repos (need a computer) ([Cloud sessions docs](https://code.claude.com/docs/en/claude-code-on-the-web)) | GitHub |

Artifacts deserve a note. They are one-page web pages hosted privately on claude.ai, up to 16 MiB. They block outside images and most outside scripts, so a game must have everything built in ([Artifacts docs](https://code.claude.com/docs/en/artifacts)). The docs don't clearly confirm they work from a phone-started cloud session, so treat them as a bonus and GitHub Pages as the dependable option. Before you make any session public, check it for secrets ([Cloud sessions docs](https://code.claude.com/docs/en/claude-code-on-the-web)).

## Conclusion

For a phone-only maker, the big shift is that **the repo is your whole toolbox**. Rules, skills, hooks, notes and save points all live there. That is because the cloud computer forgets everything else, and most famous mods were built for computer users. The winning pattern also controls costs. Short, specific rounds, a notes file that lets each new session start cold, Claude testing itself at phone size, and git undo in plain words all keep quality up and credit use down at the same time.

What's still unknown: no one has measured how many credits a play-testing loop or a toolkit like game-creator uses, and the docs leave gaps on artifacts, push alerts and account-level plugins in phone sessions. The practical answer is to try each once on a tiny test project before relying on it. **Spend your limited credits on clear plans and milestone tests, not on long chats.**
